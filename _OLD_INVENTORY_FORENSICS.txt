2) معادلات الوحدة الكبرى والتسعير اللحظي
============================================================

ProductDialog.xaml.cs يستخدم _isSyncing لمنع الدوران بين TextChanged.

2.1 من سعر الكبرى إلى سعر الصغرى — MajorPriceChanged
pieces = معامل التعبئة، وإذا كان <= 0 يصبح 1.
boxCost = سعر شراء الكبرى
boxSale = سعر بيع الكبرى

PurchasePriceBox = boxCost / pieces
SalePriceBox     = boxSale / pieces

أي:
تكلفة الحبة = تكلفة الكرتون ÷ عدد الحبات في الكرتون
سعر بيع الحبة = سعر بيع الكرتون ÷ عدد الحبات في الكرتون

2.2 من سعر الصغرى إلى سعر الكبرى — MinorPriceChanged
unitCost = تكلفة الحبة
unitSale = سعر بيع الحبة

PkgPurchaseBox = unitCost × pieces
PkgSaleBox     = unitSale × pieces

أي أن الإدخال يعمل في الاتجاهين، مع تحديث حي أثناء الكتابة.

2.3 تحويل الرصيد — PackagingValuesChanged
boxes  = عدد الوحدات الكبرى
pieces = معامل التعبئة، وإذا كان <= 0 يصبح 1

QtyBox = boxes × pieces

أي:
صافي الرصيد بالصغرى = الرصيد بالكرتون × عدد الحبات في الكرتون.

3) المعادلة اللحظية لهامش الربح وربح الحبة
============================================================

الدالة:
private void UpdateProfitCalculations()

تقرأ:
cost = PurchasePriceBox
sale = SalePriceBox

ربح الوحدة:
profit = Math.Max(0m, sale - cost)

ثم:
ProfitPerUnitText.Text =
    $"ربح {minor}: {profit:#,##0.##} {CurrencyService.CurrentSymbol}"

هامش الربح:
إذا cost > 0:
margin = decimal.Round(((sale - cost) / cost) * 100m, 1)
وإلا:
margin = 0

ثم:
ProfitMarginText.Text = $"هامش الربح: {margin}%"

ملاحظة Forensic دقيقة:
- ربح الوحدة المعروض لا ينزل تحت الصفر بسبب Math.Max.
- نسبة الهامش نفسها يمكن أن تكون سالبة إذا كان سعر البيع أقل من التكلفة.
- المعادلة هي هامش على التكلفة (Markup/Cost Margin)، وليست نسبة الربح من سعر البيع.

مثال:
تكلفة الحبة = 100
بيع الحبة = 125
ربح الحبة = 25
هامش الربح = ((125-100)/100)*100 = 25%

4) الحفظ والخدمة المحاسبية للصنف
============================================================

ProductDialog.Save() يتحقق من:
- الاسم غير فارغ.
- الرصيد >= 0
- حد الطلب >= 0
- تكلفة الشراء >= 0
- سعر البيع >= 0
- معامل التعبئة > 0
- شراء/بيع الوحدة الكبرى >= 0

ثم يبني ResultProduct بالحقول:
Code, Name, Barcode, WarehouseName, Category, Unit,
HasMajorUnit, MajorUnit, UnitsInMajor,
MajorPurchasePrice, MajorSalePrice,
Quantity, AlertThreshold, PurchasePrice, SalePrice.

الطبقة التالية:
ViewModels\InventoryViewModel.cs
تستدعي:
_accounting.AddProductAsync(dialog.ResultProduct)
أو:
_accounting.UpdateProductAsync(dialog.ResultProduct)

ثم:
Services\AccountingService.cs
يوجّه إلى:
Services\InventoryService.cs

InventoryService.AddProductAsync:
- يتحقق من عدم سلبية الكمية والأسعار.
- يجعل MovingAverageCost مصدراً لتقييم المخزون.
- إذا كانت الكمية الافتتاحية غير صفرية ينشئ InventoryMovement:
  Type = Opening
  QuantityDelta = product.Quantity
  Description = "رصيد افتتاحي للصنف"
  OccurredAt = DateTime.Now
- ثم يسجل أثر المخزون المحاسبي عبر FinancialPostingService.

InventoryService.UpdateProductAsync:
- يمنع تعديل Quantity أو MovingAverageCost أو PurchasePrice إذا اختلفت عن الحالية.
- يترك هذه الحقائق لتسوية المخزون/الحركات، وليس نافذة تعريف الصنف.

6.2 مصدر البيانات Query
في:

الاستعلام مبني على:

JOIN Invoices ON item.InvoiceId == invoice.Id

شرط:

9) ما هو "الكنز" الحقيقي الذي يجب نقله للمشروع الجديد؟
============================================================

أ) نافذة إدخال سريعة وكثيفة:
الكود -> الاسم -> الباركود
ثم المخزن -> المجموعة -> الوحدة الصغرى
ثم تفعيل اختياري للوحدة الكبرى
ثم معامل التعبئة وأسعار الكبرى
ثم الرصيد وحد الطلب وأسعار الصغرى
ثم مؤشرات الربح اللحظية.

ب) الوحدة الكبرى ليست مجرد نص:
هي علاقة رياضية حقيقية:
Major = UnitsInMajor × Minor

ج) السعران متزامنان في الاتجاهين:
Major / factor -> Minor
Minor × factor -> Major

د) الرصيد الافتتاحي بالكبرى يتحول فورياً إلى الصغرى.

هـ) الربح والهامش يظهران أثناء الكتابة دون حفظ.

و) Split View:
جدول أصناف رئيسي + بطاقة الصنف المحدد.

ز) سجل الحركة لا يُحمّل لكل الأصناف دفعة واحدة؛ يُجلب عند اختيار الصنف
On-Demand.

ح) المخزن والفلاتر والبحث تعمل فوق نفس مجموعة الأصناف.

============================================================
10) فروق يجب عدم إخفائها عن لجنة SmartLedger
============================================================

1. جدول الحركة القديم ليس الجدول الغني المطلوب حالياً؛ أعمدته الفعلية:
   البيان/الحركة + الكمية + التاريخ فقط.

2. لا يوجد في GetProductHistoryAsync حساب موثق لـ:
   Running Balance
   Unit Margin
   Movement Value

3. لذلك تصميم الجدول الجديد المقترح:
   م | التاريخ والوقت | البيان/الحركة | الكمية | الرصيد التراكمي | هامش الوحدة | القيمة
   هو تطوير محسوب، وليس "نسخاً" لميزة قديمة غير موجودة.

4. التكلفة المعتمدة للتقييم في النسخة المفحوصة هي MovingAverageCost،
   وليس مجرد PurchasePrice.

5. UpdateProductAsync يحمي الكمية وتكلفة المخزون من التعديل المباشر.

11) الخلاصة التنفيذية
============================================================

النسخة القديمة تحتوي على أفضل أفكار UX المطلوبة لشاشة المخزون:
- كثافة إدخال ممتازة.
- وضوح العلاقة بين الوحدة الصغرى والكبرى.
- مزامنة الأسعار لحظياً.
- تحويل التعبئة إلى رصيد صغرى لحظياً.
- ربح وهامش فوريان.
- مؤشرات مخزون عملية.
- فلاتر حالة سريعة.
- اختيار مخزن واضح.
- بحث مباشر.
- Split View.
- تحميل تاريخ الصنف عند اختياره.

أما ما ينبغي بناؤه في المشروع الحالي فلا يجب أن يكون نسخة حرفية:
نأخذ "فكرة الإدخال وسرعته" و"منطق المجال" و"On-Demand history"،
لكن نبني سجل الحركة الحديث بمصدر محاسبي موثوق، ونضيف صراحة:
الرصيد التراكمي + هامش الوحدة + قيمة الحركة، مع الحفاظ على الدقة
المالية وعدم تكرار منطق المخزون داخل الواجهة.
